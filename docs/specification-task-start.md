# タスクの開始ボタン仕様（issue #622）

承認後はこの仕様書を正とする。経緯と承認の記録は次の issue を参照する。

https://github.com/vektor-inc/vk-terminals/issues/622

## 前提（決まっていること）

- 「開始」ボタンの表示文言・読み上げ名・ツールチップ・確認ダイアログの文言は、VK Orchestrator が書き出す宣言 `startCommand` の完成文をそのまま使う。宣言の形は vektor-inc/vk-orchestrator#979（PR #981）で決まっている（vk-orchestrator の `docs/tasks-widget-schema.md`「開始の依頼（startCommand / start-task。issue #979）」節）。
- 「開始」ボタンは `startCommand` があるタスクにだけ出す。今は「承認待ち」かつ編集できるタスクだけに載る。古い VK Orchestrator と組み合わせたときはボタンを出さない。
- 押すと、`commands.jsonl` に `start-task` の依頼を 1 行追記する。追記するのは `{ id: "start-…", action: "start-task", taskId, expected, requestedAt }`。受け付けたかどうかは返ってこず、カードが「実行待ち」へ移ることで分かる。同じタスクで二重に押しても、2 回目は VK Orchestrator 側の照合で捨てられるので害はない。

## 編集ボタン

- 「編集」ボタンを歯車アイコンだけのボタンにする。読み上げ名は「「<タスク名>」を編集」（保存中は「（保存中のため操作できません）」、開始中は「（開始中のため操作できません）」付き）。開閉の状態の伝達（`aria-expanded` / `aria-controls`）、フォーカスの戻し先は従来のものを引き継ぐ。
- 移行の手がかりとして、ツールチップに「編集」と出し、CHANGELOG に「編集ボタンは歯車アイコンになりました（位置は右端のまま）」と書く。

## アイコン

- ▶ は文字ではなく、アイコン集 `renderer/icons/ui.svg` に `play` を足して描く。macOS では記号の ▶ が絵文字として表示されることがあり、#620 でペインヘッダーをアイコンに揃えた流れにも合わせる。歯車には既存の `settings` を使う。
- スマートフォン版でもアイコンが出るように、配信する静的ファイルの一覧（`utils/staticRoutes.js`）に `/icons/ui.svg` を足す。

## 配置と見た目

- 開始と歯車を 1 つのまとまりにして、状態バッジの行の右端に置く（左に開始、右に歯車）。開始が出ないカードでも歯車が常に右端に来て、一覧で位置が揃う。
- サイドバーが狭くて折り返すときは、2 つまとめて次の行の右端へ送り、開始だけが前の行に残らないようにする。
- 「開始」の幅を固定し（`min-width`）、「開始中…」に変わっても歯車が動かないようにする。
- 宣言の `label` が長いときは、最大 8em で省略（`text-overflow: ellipsis`）し、カードからはみ出させない。
- 「開始」は緑の枠線と緑の文字（`#2ea043` / `#3fb950`、塗りなし）。緑の塗りは「保存」「開始する」など確定ボタンに取っておく。高さ・文字の大きさは歯車（従来の編集ボタン）に揃える。

## 確認ダイアログ

- 確認ダイアログを出すのは、宣言に `confirm` があるとき（自動マージがオンのタスク）だけ。
- PC 版では、アプリ内のダイアログ（`renderer/app.js` の `openStartTaskConfirmDialog`）を使う。Electron の `window.confirm` は「OK」が既定の選択になり、「キャンセルを既定にする（Enter で確定しない）」という取り決めを満たせないため。
  - 作りは既存の「閉じる」確認ダイアログ（`openCloseConfirmDialog`）と同じで、キャンセルが初期フォーカス、Escape・背景クリックでキャンセル。ボタンは左にキャンセル、右に `confirm.confirmLabel`（緑の塗り）を置く。見出しは `confirm.title`、本文は `confirm.body`。
  - 共有レンダラ（`renderer/widgetView.js`）には、非同期の `deps.confirmStart` として注入する。
- スマートフォン版はブラウザ標準の確認（`window.confirm`）にして、見出しと本文だけを出す。宣言の取り決めでも「確定ボタンの文言を描けない画面は見出しと本文だけでよい」と認められている。
- 採らなかった案: 既存の確認ダイアログ 3 つを共通部品にまとめる案。範囲が広がって、壊れるおそれも増えるため。

## 「開始中…」

- 押した直後から、ボタンを「開始中…」にして `aria-disabled` と `aria-busy` で押せなくする。ネイティブの `disabled` は使わない（フォーカスが body へ落ちるのを防ぐため。編集ボタン・再取得ボタンと同じ作法）。
- 終える条件: 次に届いた一覧で、そのタスクの `startCommand` が無くなったとき、またはタスクが一覧から消えたとき。状態の名前から判断することはしない（どの状態で開始できるかを画面側で判断しない、という取り決めに合わせるため）。
- 追記に失敗したら、すぐに元に戻し、カードの下に「開始を依頼できませんでした。もう一度押してください」と出す（`role=alert`）。
- 60 秒たっても反映されなければ、元に戻し、「開始を確認できませんでした。オーケストレーターが動いているか確かめて、もう一度押してください」と出す（`role=alert`）。60 秒は再取得ボタンの待ち時間と同じ。二重に押しても害が無いので、長く待たせない。
- 失敗の表示は、押し直したとき、または `startCommand` が無くなったときに消す。
- 開始中は、同じカードの歯車も押せなくする。状態が切り替わる途中で編集されるのを防ぐため。
- 開始に成功してボタンが消えたときは、フォーカスが開始ボタンにあった場合に限り、同じカードの歯車へ移す。

## 編集との関係

- そのタスクが保存中のときは「開始」を押せなくし、読み上げ名とツールチップの末尾に「（保存中のため開始できません）」を添える。
- 編集パネルを開いているが変更が無いときは押せる。押したらパネルを閉じる。
- 編集パネルに未保存の変更があるときは「開始」を `aria-disabled` にし、読み上げ名とツールチップの末尾に「（編集中の変更を保存してから開始できます）」を添える。下書きを変えた時点で（一覧の書き直しを待たずに）切り替える。

## 依頼ファイルが未設定のとき

- `commands.jsonl` の場所が設定されていないときは「開始」ボタンを出さない。再取得ボタンと同じ扱い。歯車は従来の「編集」と同じく出したままにする。

## 反映の検知漏れを防ぐ

- 別のタスクの編集パネルを開いている間は、サイドバーの書き直しを見送る作りになっている（PC 版 `renderer/app.js`、スマートフォン版 `renderer/mobile.js`）。開始中のタスクがあるときは書き直し（`hasStarting()`）、反映を見落としてタイムアウトするのを防ぐ。
- プルダウン（select）にフォーカスがある間も、ピッカーを閉じないよう書き直しを見送る。ただし、届いた一覧で開始中のタスクが終わるとき（`isStartingSettledBy()`）だけは書き直す。書き直しはその 1 回だけで、フォーカスはプルダウンへ戻す。編集パネルを開くと初期フォーカスがプルダウンへ移るため、これが無いと別タスクの編集を開いただけで反映を見落とす。

## 受け側の検証

- 宣言の受け取り（`utils/widgetContract.js` の `sanitizeStartCommand`）で `startCommand` を残し、文字数の上限で切り詰める。`label` か依頼の断片が無い宣言、別のカードを指す宣言（`command.taskId` がカード ID と違う）は落とす。
- 依頼を組み立てる関数（`buildStartCommandLine`）は、既存の状態変更の依頼とは別に作る。既存の依頼と混ぜると、一括確定の依頼（`apply-batch`）に紛れ込める形になるため。`main.js` の `submitWidgetCommand` が `id`（接頭辞 `start-`）と `requestedAt` を付ける。
- 文言はすべてプレーンテキスト（`textContent`）で描き、`innerHTML` は使わない。
